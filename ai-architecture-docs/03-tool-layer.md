# 03: Tool Layer - The System's Hands

## 1. Concept Overview

While the Memory Layer gives an AI contextual awareness, the **Tool Layer** gives it agency. Without tools, an LLM is merely a text generator. The Tool Layer provides a secure, structured interface that allows the AI to execute actions in the physical or digital world.

**What problem it solves:**
LLMs cannot access live data natively (like real-time weather), nor can they perform state-altering actions (like booking a flight, updating a database, or canceling a subscription). The Tool Layer solves this by exposing deterministic software functions to the stochastic LLM.

**Why it exists in production:**
To safely contain agentic execution. In production, an AI cannot simply run random Python code. The Tool Layer mandates strict schemas, access controls, and boundary validations on what the AI can invoke.

---

## 2. Responsibilities of the Layer

1. **Tool Definition & Schema Registration:** Maintaining a registry of available functions mapped to JSON Schemas that the LLM can understand.
2. **Action Execution (API Orchestration):** Performing the actual HTTP calls, SQL queries, or internal script executions when invoked by the Orchestrator.
3. **Error Normalization:** Translating ugly 500 API errors into natural language components the LLM can use to self-correct.
4. **Tool Selection Strategies:** Determining which subset of tools to expose to the LLM in the current context (preventing context bloat).

---

## 3. Workflow Placement

The Tool Layer operates strictly below the Orchestrator and LLM Reasoning layers. It never talks directly to the user.

```text
[ Orchestrator Layer ] ◄──► [ LLM Reasoning Layer ]
         │
         ▼ (Invokes Tool via JSON payload)
==========================
    TOOL LAYER
==========================
   ├── [ Weather API ]
   ├── [ Database Query ]
   └── [ Ecommerce Cart API ]
         │ (Returns structured data)
         ▼
[ Orchestrator Layer ] (Passes result back to LLM)
```

---

## 4. Internal Architecture

The Tool Layer is built around a **Tool Registry**. 

1. **The Registry:** A dictionary of function interfaces. Each function requires a meticulously crafted JSON Schema describing its purpose, arguments, and required fields.
2. **The Executor:** A sandboxed environment or dedicated API client that takes the JSON payload generated by the LLM, validates the arguments statically (using Pydantic, Zod, etc.), and runs the code.
3. **The Data Mapper:** Takes the raw JSON response from external systems and trims out useless metadata before handing it back to the LLM, saving tokens.

---

## 5. Implementation Approaches

### Simple Startup Version
Hardcoded Python functions decorated with framework-specific annotations (e.g., Langchain `@tool`). The system passes all 5 available tools to the LLM in every single prompt. 

### Scalable Production Version
A dedicated Microservice handles execution. Tools are strictly typed using Pydantic. Strict validation layers ensure the LLM didn't invent invalid arguments. The Orchestrator dynamically passes only the relevant tools (e.g., if intent is "WEATHER", only pass the weather tool, omit the database tools).

### Enterprise Version
Tools require multi-level Authentication based on the user's JWT. A permissions matrix guarantees the LLM cannot invoke the `delete_database` tool unless the `user_role = ADMIN`. Complex tasks use API gateways to orchestrate multi-step tool calls natively. All tool outputs are aggressively sanitized for PII leakage before touching the LLM again.

## 6. Example Implementation

Here is a pseudo-code implementation showing tool registration and execution using modern tool calling patterns:

```python
class ToolRegistry:
    def __init__(self):
        self.tools = {}

    def register(self, name, description, schema, execute_func):
        self.tools[name] = {
            "description": description,
            "schema": schema,
            "execute": execute_func
        }
        
    def get_schemas_for_llm(self, intent_context):
        # Dynamic tool selection strategy: 
        # Only return tools relevant to the current orchestrator context
        return [t["schema"] for t in self.filter_tools_by_context(intent_context)]

    def execute_tool(self, name, arguments_dict):
        # 1. Look up tool
        tool = self.tools.get(name)
        if not tool:
            return "Error: Tool not found."
            
        # 2. Strict validation of LLM output
        if not static_validate(arguments_dict, tool["schema"]):
            return "Error: Invalid arguments provided. Please retry."
            
        # 3. Execution
        try:
            return tool["execute"](**arguments_dict)
        except Exception as e:
            return f"Error executing tool: {str(e)}"

# Example Tool: Add to Cart
def api_add_to_cart(user_id, item_sku, quantity):
    # Perform actual DB/API logic
    db.cart.insert({"user": user_id, "item": item_sku, "qty": quantity})
    return {"status": "success", "message": f"Added {quantity} of {item_sku}"}
```

## 7. Technology Options

* **Function Calling Support (LLM side):** OpenAI Tools API, Anthropic Tool Use, Gemini Functions.
* **Validation:** Pydantic (Python), Zod (Node.js).
* **Execution Environments:** Serverless functions (AWS Lambda), Dockerized Sandboxes (E2B, AutoGPT workspaces) for running arbitrary code.
* **API Orchestration:** Zapier, Make, n8n, or raw REST/GraphQL clients.

**When to use each:** Use raw code for internal, highly trusted APIs. If giving the LLM a Python REPL tool (letting it write and run code), you **must** use a Dockerized sandbox like E2B to prevent lateral network attacks.

---

## 8. Scaling Considerations

* **At 1k Users:** Direct synchronous execution inside the main API process is acceptable.
* **At 10k Users:** Third-party API rate limits (e.g., calling Stripe or Shopify) will become the primary bottleneck. You must implement robust backoff, throttling, and API key pooling in the Tool Layer.
* **At 100k Users:** Tool execution must be completely asynchronous. The user sends a request, the LLM queues a Tool call, a background worker (Celery/RabbitMQ) executes the heavy DB query, and server-sent events (SSE) notify the UI when the tool completes.

---

## 9. Failure Handling

* **The "Hallucinated Argument" Error:** LLMs frequently invent parameters (e.g., `date="yesterday"` instead of ISO format). The Tool Layer must catch this schema violation and *feed the error back to the LLM* in a retry loop: *"Validation Error: 'yesterday' is not YYYY-MM-DD. Fix it."*
* **API Outages:** If an external shipping API goes down, the tool must return an explicit, prompt-friendly string: *"The shipping provider API is currently down. Tell the user you cannot check their status right now."* (Never expose ugly stack traces back to the LLM).

---

## 10. Cost Optimization

1. **Tool Output Trimming:** APIs often return massive JSON payloads (20kb of headers and metadata). The Data Mapper must strip this down to *only* the data the LLM needs before passing it back, saving huge token costs on the subsequent reasoning step.
2. **Read vs. Write Policies:** Only use the expensive LLM to trigger *writes* (mutations). For simple *reads* (e.g., "list my orders"), the Intent Layer should intercept the request and trigger the API directly, mapping the JSON to a UI widget without ever invoking the LLM reasoning loop.
